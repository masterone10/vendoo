# إصلاح البنية الهندسية لاتصالات أرشيف Supabase PostgreSQL وضمان استقرار الـ Pool

خطة هندسية تفصيلية لحل المشاكل الجذرية لاتصالات Supabase، وإلغاء ظاهرة هدم وإعادة بناء الـ Pool المتكررة، وضبط الاتصال عبر Supabase Session Pooler (منفذ 5432) مع حماية مصادقة SCRAM وتثبيت حجم الاتصالات وتأمين البيانات محلياً في SQLite دون أي فقدان أو تكرار.

---

## القرارات المؤكدة مع المشرف (User Review & Critical Decisions)

> [!IMPORTANT]
> بناءً على إجابات الاستيضاح، تم تثبيت الخيارات الهندسية والتشغيلية التالية:
> 1. **منفذ ونوع الـ Pooler**: الانتقال رسميًا إلى **Session Pooler على المنفذ 5432** (`aws-1-eu-central-1.pooler.supabase.com:5432`) لضمان استقرار الاتصالات المستمرة لتطبيق Node.js Backend طويل التشغيل، وتجنب مشاكل المعاملات الخاصة بـ PgBouncer/Supavisor Transaction mode على 6543 ومشاكل الـ Prepared Statements.
> 2. **حجم الـ Pool وسياسة المعالجة**: استخدام **Pool واحد مشترك على مستوى العملية بالكامل (Single Process-wide Singleton)** بحد أقصى **3 اتصالات فقط**، ومعالجة الدفعات بتسلسل محكوم (Serialized Batches) لمنع استنزاف موارد الـ Pooler وتجنب تنافس المصادقة.
> 3. **معالجة الانقطاع المؤقت والأرشفة**: تطبيق تراجع أسي (Exponential Backoff) مع عشوائية مدروسة (Jitter)، مع **حفظ واحتفاظ كامل بنسبة 100% بكافة السجلات والأحداث محلياً في SQLite** حتى يتم تأكيد الأرشفة السحابية بنجاح دون أي فقدان أو تكرار.

## 1. Overview & Root Cause Analysis (نظرة عامة والتحليل الجذري)

### المشكلة المكتشفة في سجلات 24 أكتوبر 2026:
- أخطاء `Connection terminated due to connection timeout`.
- أخطاء `Timeout while waiting for message in state SCRAM final`.
- أخطاء `ECLIENTSOCKETCLOSED` أثناء `auth_scram_first_wait` و `auth_scram_final_wait`.
- اتصالات تنجح ثم تتكرر عمليات فتح وإغلاق الاتصالات بشكل دوري ومزعج.

### السبب الجذري المؤكد (Proven Root Cause):
1. **هدم الـ Pool عند إغلاق الاتصالات الخاملة**: في كود `server/supabaseClient.ts` الحالي، كان معالج الأحداث `pool.on('error')` يقوم باستدعاء `resetSupabasePool()` فور حدوث أي انقطاع لاتصال خامل (Idle Connection Drop) من جهة السيرفر. يقوم مزود Supavisor تلقائيًا بإنهاء السوكتات الخاملة بعد دقيقة، فيقوم تطبيق Node بإنهاء الـ Pool بالكامل ومسح الكائن `pool = null`.
2. **عواصف المصادقة المتكررة (SCRAM Auth Storms)**: عند قدوم الاستعلام التالي، يجد التطبيق أن `pool` فارغ، فينشئ Pool جديدًا ويبدأ في طلب اتصالات جديدة من الصفر، مما يطلق مصادقة SCRAM-SHA-256 متكررة لكل دفعة أو فحص صحة (`pre-flight ping`). ومع وجود محاولات متوازية من الفحص الدوري والأرشفة، يتأخر الرد فيحدث `Timeout while waiting for message in state SCRAM final` و `ECLIENTSOCKETCLOSED`.
3. **تدمير الـ Pool أثناء معالجة الاستعلام**: في دالة `pgQuery()` كان أي خطأ عابر يؤدي مباشرة إلى استدعاء `resetSupabasePool(p)`، مما يقطع الاتصالات السليمة الأخرى الجارية في نفس اللحظة.
4. **استخدام Transaction Pooler (6543) بدلاً من Session Pooler (5432)** لتطبيق Backend دائم، حيث يعامل 6543 الجلسات بشكل متقطع مع كل معاملة.

## 3. Key Product & Technical Decisions (القرارات الهندسية والتنفيذية)

### أ. إدارة الـ Pool كـ Singleton محمي
- حظر إنشاء أي كائن `new Pool()` خارج مكان مركزي واحد في `server/supabaseClient.ts`.
- حظر استدعاء `resetSupabasePool()` عند إغلاق الاتصالات الخاملة. في مكتبة `pg`، عندما يغلق السيرفر اتصالاً خاملاً، يقوم الـ Pool تلقائياً بإزالته واستبداله عند الحاجة؛ ولا يجوز هدم الـ Pool كاملاً.
- منع تعارض عمليات إعادة الضبط في حال حدوث خطأ كارثي عبر `poolResetPromise` متزامن، يضمن عدم تكرار الإنشاء أو تداخل الاتصالات.

### ب. التهيئة الدقيقة لـ Session Pooler (Port 5432)
- استبدال المنفذ 6543 بالمنفذ 5432 المخصص لـ Session Pooler مع اسم المضيف المعتمد `aws-1-eu-central-1.pooler.supabase.com`.
- تفعيل `keepAlive: true` و `keepAliveInitialDelayMillis: 10000` للحفاظ على حيوية الاتصال ومنع الـ NAT/Firewall من إسقاط الاتصال.
- ضبط مهلة الاتصال `connectionTimeoutMillis: 20000`، ومهلة الاستعلام `statement_timeout: 30000`.
- ضبط حجم الـ Pool بحد أقصى `max: 3` اتصالات، وهو الحجم المثالي لأحمال الأرشفة الخلفية في هذا التطبيق.

### ج. تتبع السياق وقياس الأداء بدقة (Correlation IDs & Timing Metrics)
- إضافة `correlationId` فريد لكل استعلام أو دفعة أرشفة لتتبع دورة حياة الاتصال.
- تقسيم القياسات الزمنية في السجلات بدقة:
  - `tWaitPool`: زمن انتظار الحصول على اتصال متاح من الـ Pool.
  - `tAuthConnect`: زمن إنشاء الاتصال والمصادقة إذا كان الاتصال جديداً.
  - `tExecution`: زمن تنفيذ كود SQL على قاعدة البيانات.
- إلغاء طباعة تحذيرات عشوائية عن إغلاق المقابس الطبيعي دون سياق واضح.

### د. حماية كاملة للبيانات والتراجع الأسي مع Jitter
- جميع السجلات تظل محفوظة محلياً في SQLite مع تحديث الـ Checkpoints فقط بعد إتمام الإدخال بنجاح في Supabase (`ON CONFLICT DO NOTHING`).
- عند حدوث انقطاع مؤقت في الشبكة، يتم تأجيل الدفعة التالية باستخدام `backoffMs = Math.min(300000, baseDelay * 2^failures) + jitter`.
- منع تشغيل أكثر من عملية أرشفة متوازية (`isArchiving` Guard + Mutex).

## 4. Implementation Steps & Target Files (خطوات التنفيذ)

### المرحلة 1: ضبط وإصلاح `server/supabaseClient.ts`
- تحديث استخراج وتوليد الـ URL للتحويل التلقائي الآمن إلى Session Pooler (منفذ 5432) في حال استخدام عنوان Pooler الخاص بـ Supabase.
- إعادة هيكلة `getSupabasePool()` لمنع إعادة بناء الـ Pool عند الأخطاء الخاملة العادية.
- إعادة كتابة `pgQuery()` لاستخدام الاتصال المشترك مع `correlationId`، وقياس أزمنة الاتصال والانتظار والتنفيذ بشكل منفصل.
- توفير آلية إغلاق آمنة ونظيفة (`gracefulShutdown`) عند إنهاء العملية.

### المرحلة 2: ضبط `server/supabaseArchiveWorker.ts`
- مراجعة استدعاءات `triggerArchivePass` لضمان التسلسل التام (Serialized Execution) دون أي تداخل.
- استبدال رسائل الخطأ الحادة بمعالجة هادئة للتراجع الأسي مع Jitter.
- التأكد من عدم هدم الـ Pool المشترك عند تعثر الـ Pre-flight Ping.

### المرحلة 3: مراجعة نقاط الاتصال في `server.ts` وباقي الملفات
- التأكد من أن مسارات الخادم (API Routes) تستدعي `pgQuery()` ولا تنشئ أي اتصالات فرعية مباشرة أو تغلق الـ Pool.
- فحص دوال إغلاق الخادم (`process.on('SIGTERM')`, `process.on('SIGINT')`) لإغلاق الـ Pool المشترك بطريقة نظيفة.
